# Recora Development Domains

- Status: **Accepted**
- Decision date: **2026-08-04**
- Decision source: GitHub Issue #156 and the latest OWNER decision
- Scope: Recora全体の開発、進捗、Issue分類に使用する最上位の機能領域

## 1. 目的

Recoraの開発対象を、画面、業務処理、データ基盤が混在しない形で整理する。

今後、全体構成、達成度、残作業、ロードマップ、GitHub Issue、PRの主対象は、次の9領域を最上位分類として扱う。

```text
Recora
├─ 1. 公開サイト
├─ 2. 顧客オンボーディング
├─ 3. 顧客画面
├─ 4. 管理画面
├─ 5. プロンプト・測定設計
├─ 6. AI測定・分析
├─ 7. 品質・公開・レポート
├─ 8. 顧客・契約・権限
└─ 9. 共通基盤
```

この分類は既存Phase、画面内分類、内部層、PostgreSQL Schemaを廃止または改番するものではない。

## 2. 他の分類軸との関係

```text
9開発領域
= 何を開発しているか

Phase
= どの順番・工程で開発するか

画面内分類
= 顧客画面・管理画面の下位構成

内部層 / Schema
= どの技術領域へ実装するか
```

同じタスクには複数の軸を併記できるが、9開発領域の主領域は必ず1つにする。

例:

```text
タスク: オンボーディングで確定したPromptを正式保存する

主領域: 5. プロンプト・測定設計
関連領域: 2. 顧客オンボーディング
実装Phase: Phase 5
技術層: control / measurement
```

9領域の番号をPhase番号として扱ってはならない。

## 3. 9開発領域

### 3.1 公開サイト

契約前の利用者へRecoraを説明し、問い合わせ、診断、登録、契約開始へつなげる領域。

主な対象:

- トップページ
- サービス・機能紹介
- 課題別ページ
- 料金
- 導入事例
- 無料診断
- FAQ
- 問い合わせ
- 利用開始導線
- 法務ページ
- 公開SEO、metadata、sitemap、robots

含めないもの:

- ログイン後の顧客利用画面
- 契約状態や支払い事実の正式管理
- 顧客Projectの初期設定処理

### 3.2 顧客オンボーディング

顧客がRecoraを使い始めるための入力、確認、保存、初回開始体験を提供する領域。

主な対象:

- サイトURL入力と解析結果の確認
- ブランド、事業内容、カテゴリの確認
- 対象地域と言語
- Persona、Topic、Prompt候補の確認
- 顧客による修正・追加・削除
- 最終確認
- 途中保存・再開
- 初期設定完了
- 初回測定開始導線

境界:

- 顧客が操作する画面と入力体験は本領域
- Persona、Topic、Promptの生成・分類・確定ロジックは「5. プロンプト・測定設計」
- 組織、契約、利用権限の正式状態は「8. 顧客・契約・権限」

### 3.3 顧客画面

契約後の顧客が、公開済みの安全な結果、変化、根拠、改善情報を日常的に確認する領域。

正式な主要画面構成:

- 概要
- 推移・変化
- ブランド・競合
- Persona・Topic
- Prompt
- AI回答
- 引用・参照元
- ブランド印象
- 改善提案
- 設定・連携

境界:

- 顧客画面はcustomer-safeな`api`または`publication` projectionを読む
- 生provider payload、未審査結果、内部監査、費用、内部reason codeを直接参照しない
- レポートを見る操作は本領域
- レポートを検査、生成、公開、停止する処理は「7. 品質・公開・レポート」

### 3.4 管理画面

Recora運営者が顧客、測定、品質、公開、障害、コスト、設定を安全に操作するUI領域。

正式な8領域:

1. 運用ホーム
2. 顧客管理
3. 測定管理
4. 品質・例外レビュー
5. 公開管理
6. 障害・監査
7. 利用量・コスト
8. 管理設定

顧客管理内にお問い合わせ管理を含む。

境界:

- 本領域は管理者が見る画面、ナビゲーション、操作体験を所有する
- Role、Capability、Scopeなどの業務上の権限モデルは「8. 顧客・契約・権限」
- Command receipt、Outbox、認可強制、監査保存などの共通機構は「9. 共通基盤」
- 管理者ブラウザからDBを直接更新しない

### 3.5 プロンプト・測定設計

何を、誰の視点で、どの条件・指標対象として継続測定するかを確定する領域。

主な対象:

- 事業・カテゴリ分析
- Persona設計
- Topic設計
- Intent grouping
- Prompt生成
- branded / non-branded / comparison / citation分類
- Core / Robustness / Diagnosticのpanel role
- metric eligibility
- 測定対象AIモデルと測定条件
- Prompt設定の確定
- 設定version、count、hash
- 測定開始前の設計整合性検証

境界:

- Prompt自体の重複、汚染、用途不整合などの品質は本領域
- provider実行、回答取得、retryは「6. AI測定・分析」
- 実行結果の品質、公開可否は「7. 品質・公開・レポート」

### 3.6 AI測定・分析

確定した測定設計を使ってAIへ質問し、回答・引用・言及を取得、解析、数値化する領域。

主な対象:

- Measurement RunとItemの作成
- Queue投入とWorker実行
- AI provider / model呼び出し
- Attempt、timeout、retry、idempotency
- 回答とprovider evidenceの保存
- 引用URL取得・正規化
- ブランド・競合言及抽出
- 順位・掲載位置判定
- ブランド印象・sentiment解析
- 指標計算と再計算
- 利用量・費用記録
- 再解析

境界:

- 分析結果を生成するところまでが本領域
- 結果が信頼できるか、再測定すべきか、公開可能かの判断は「7. 品質・公開・レポート」
- Queue、Scheduler、ログなど再利用可能な実行機構は「9. 共通基盤」

### 3.7 品質・公開・レポート

測定・分析結果を検査し、customer-safeな不変の公開版として顧客へ届ける領域。

主な対象:

- 測定完全性チェック
- 回答・解析品質チェック
- 指標成立チェック
- 品質findingと例外判定
- 再測定・再解析判定
- 改善提案品質チェック
- 公開候補生成
- `ready / approved / published`の分離
- 公開可否判定と承認
- 不変な公開版
- current publication pointer
- 公開停止、差し替え、復元
- PDF、CSV、共有レポート生成
- レポート生成履歴

境界:

- 分析値を計算する処理は「6. AI測定・分析」
- 顧客が公開版を見るUIは「3. 顧客画面」
- 管理者が例外・公開を操作するUIは「4. 管理画面」

### 3.8 顧客・契約・権限

誰が、どの組織・Projectに属し、どの契約条件で何を利用できるかを管理する業務領域。

主な対象:

- 顧客組織
- Project
- 顧客アカウント
- 招待
- Membership
- 顧客ライフサイクル
- 契約・subscription状態
- 請求・支払い事実
- Plan policy
- Entitlement snapshotとcurrent pointer
- 顧客アクセス判定
- 管理者account、Role、Capability、Scope
- 契約停止、再開、解約、復旧

境界:

- 本領域は「誰が何を利用できるか」という業務事実とルールを所有する
- Supabase Auth、Session、RLS、監査保存などルールを強制する汎用技術は「9. 共通基盤」
- 料金を説明するページは「1. 公開サイト」
- 契約を管理者が操作する画面は「4. 管理画面」

### 3.9 共通基盤

他の8領域が共同で利用する技術、セキュリティ、運用、開発基盤。

主な対象:

- DatabaseとMigration
- AuthとSession基盤
- RLSとtenant isolationの強制
- Command receiptとEvent
- Audit logの共通保存機構
- Outbox
- Read Model更新基盤
- Queue、Worker、Schedulerの共通機構
- 通知・メール基盤
- 外部API接続基盤
- Secret管理
- セキュリティ検査
- ログ、メトリクス、トレーシング、アラート
- Backup、復旧、可観測性
- CI、preflight、テスト、branch protection
- Agentic SDLC、Issue、Exec Plan、release運用

境界:

- 業務固有の状態・判断は対応する1〜8の領域へ置く
- 複数領域から再利用される仕組みだけを本領域へ置く
- 「DBを使う」という理由だけで業務機能を共通基盤へ分類しない

## 4. 既存構造との対応

### 4.1 既存の2画面・3内部層・横断機能

| 既存構造 | 主な9領域 |
|---|---|
| 顧客向け画面 | 3. 顧客画面 |
| 管理者向け画面 | 4. 管理画面 |
| 公開レポート層 | 7. 品質・公開・レポート |
| 運用制御層 | 5、6、7、8、9に責務別で分割 |
| 測定・証跡層 | 主に6、一部9 |
| 横断機能 | 主に9、一部8 |

既存の`api / publication / measurement / control / audit`は技術配置として維持する。

### 4.2 既存Phase

| Phase | 主な9領域 |
|---|---|
| Phase 3 | 8. 顧客・契約・権限、9. 共通基盤 |
| Phase 4 | 8. 顧客・契約・権限、9. 共通基盤 |
| Phase 5 | 2. 顧客オンボーディング、5. プロンプト・測定設計 |
| Phase 6 | 6. AI測定・分析、9. 共通基盤 |
| Phase 7 | 6. AI測定・分析、7. 品質・公開・レポート |
| Phase 8 | 3. 顧客画面 |
| Phase 9 | 4. 管理画面 |
| Phase 10 | 1. 公開サイト |

Phaseは実装順・所有範囲であり、9領域の番号とは独立する。

## 5. IssueとPRの分類契約

新規Issueでは原則として次を記録する。

```text
主領域: 9領域から必ず1つ
関連領域: 必要な場合のみ0件以上
実装Phase: 既存Phaseまたは未確定
技術層: api / publication / measurement / control / audit / その他 / 該当なし
```

ルール:

1. 主領域は成果物の中心責務を持つ領域にする。
2. ファイル数やDB Schemaだけで主領域を決めない。
3. UIと内部処理にまたがる場合も、Issueの主要な受け入れ条件から主領域を1つ決める。
4. 複数の主目的があるIssueは、独立して検証できる子Issueへ分割する。
5. Admin P0という名称だけで「4. 管理画面」へ分類しない。
6. Prompt品質は5、測定結果品質は7へ分類する。
7. レポート生成・公開は7、顧客による閲覧は3へ分類する。
8. 契約・Entitlementの業務状態は8、強制機構は9へ分類する。

PRではIssueの分類を引き継ぎ、変更後に主領域が変わった場合はIssueへOWNER判断を記録する。

## 6. 進捗・達成度の判定

9領域の進捗は、画面や型が存在するだけで完成扱いにしない。

達成度では少なくとも次を区別する。

- 設計・契約のみ
- 試作・fixture・モック
- local-only実装
- masterへ統合済み
- DBへ正式保存可能
- 実データで動作
- 権限・監査・失敗処理あり
- 本番で継続運用可能

Draft PR、未merge branch、設計書のみ、モック値、手動の単発成功は、その状態を明記して評価する。

## 7. 移行ルール

- 過去IssueとPRを9領域へ一括改名・書き換えしない。
- 進行中Issueは、次回更新時に主領域・関連領域を追記できる。
- 既存Phase文書、顧客画面10領域、管理画面8領域、DB Schema名は維持する。
- 9領域と既存正本が競合する場合は、最新OWNER決定、対象領域の正本、本書の順で確認する。
- 開発領域自体を追加、削除、統合、改名する場合は、本書と`docs/README.md`を同じIssueで更新する。

## 8. 非目標

本書は次を決定しない。

- 個別機能の最終仕様
- Phaseの実装順変更
- PostgreSQL Schemaの物理配置変更
- 顧客画面・管理画面の具体的デザイン
- Pricing、決済provider、契約ポリシー
- 各領域の現在達成度

それらは該当Issueと対象領域の正本で決定する。
